Independent Biomedical Engineering Project

From abdominal sound capture to a personal SenseLoop.

MOM is a low-cost prototype for abdominal-acoustic data capture and analysis. I designed the hardware around an ESP32, MAX4466 microphone amplifier, and stethoscope-based acoustic coupling, then built software for recording, signal-quality checks, personalized check-ins, uncertainty-aware estimates, multi-user sharing, preference learning, and review.

The engineering problem

Abdominal acoustics are messy. A useful prototype has to deal with contact pressure, sensor placement, motion, environmental noise, amplifier gain, clipping, network reliability, and repeatability before any model is worth discussing.

Built

Low-cost capture stack

Classic ESP32-WROOM-32, MAX4466 manual-gain microphone amplifier, and stethoscope coupling form the physical acquisition system.

Iterated

Noise + contact controls

Repeated hardware testing focused on movement artifacts, environmental noise, microphone gain, sensor position, mounting pressure, headroom, and stable contact.

Software

Acquisition + review

Python and Flask/Waitress services receive sensor windows, extract acoustic features, reject bad-quality input, save guided sessions, and power the web interface.

MOM SenseLoop V3

V3 turns the capture system into a human-in-the-loop personal learning prototype. The goal is not to claim that a sensor can “know” hunger. It is to test whether a person's abdominal-acoustic patterns can add useful information to their own repeated self-reported check-ins.

Select the wearerSeparate profiles let multiple people share one physical device without mixing recordings, labels, models, or food-preference history.
Record a guided sessionThe interface checks connection, clipping, movement/noise, and signal quality while collecting a short acoustic session.
Add the labelThe user reports current hunger from 0–10 and can add meal timing, activity, unusual-noise, and sensor-position context.
Aggregate the recordingSession features include candidate bowel-sound event rate/duration, RMS, spectral bandwidth, band power, centroid, entropy, and quality indicators.
Compare three model viewsTime-only baseline versus sounds-only versus a personalized model combining sound with the user's own context and previous check-ins.
Abstain when neededPoor signal quality, insufficient history, weak maturity, or high uncertainty can return “Not enough information.”
Ask, don't declareNotifications are gated by quality, recent-period agreement, model maturity, and cooldown, then ask the wearer to confirm the estimate.
Learn preferencesOptional savory/sweet/fresh/warm/crunchy/filling selections and practical constraints can rank food ideas. DoorDash is only a user-initiated handoff.
Product wording: “Estimated self-reported hunger based on your past patterns.”

Guest Mode: show the project, not somebody's profile

The device-hosted V3 site now separates a public educational surface from the private user application. A visitor can understand MOM without getting access to a real person's sensor stream or history.

Guest Mode can show

  • What MOM is and why it exists
  • How the hardware/software loop works
  • A clearly labeled illustrative sample session
  • How check-ins, uncertainty, and preference learning work
  • Claim boundaries and limitations

Guest Mode cannot show

  • Profile names
  • Live ESP32 sensor readings
  • Recorded sessions or hunger check-ins
  • Food-preference history
  • Personal model outputs
  • Private API data

Remote private-dashboard access remains access-code protected. The physical ESP32 ingestion endpoint remains local-network only.

Claim boundaries

The strongest version of the project is the accurate one. The engineering work does not need inflated clinical language.

Appropriate

  • Low-cost prototype for abdominal-acoustic data capture and analysis
  • Independent biomedical engineering project
  • Personalized association model with uncertainty
  • Preference learning from previous choices
  • Cross-corpus acoustic signal-processing research

Not supported

  • Diagnostic device
  • Detecting gastrointestinal disease
  • Clinical detector
  • Disease-screening system
  • Medically validated device
  • Mind-reading or thought decoding

Engineering evidence to keep building

The highest-value next step is external technical evaluation, backed by a clean record of how the device evolved.

Physical evidence

Dated prototype photographs, sensor mounting images, wiring diagrams, and demonstration footage.

Iteration evidence

Technical-testing logs, failed approaches, design revisions, noise/contact troubleshooting, and configuration-lock records.

External review

Engineering feedback plus faculty, clinician, or biomedical-device evaluation focused on measurement quality, usability, and next experiments.
